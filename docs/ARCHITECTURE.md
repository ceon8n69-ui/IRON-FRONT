# Архитектура и границы первого среза

## Компоненты

Один репозиторий, один серверный модуль `app`, три процесса: API, worker и bot. Клиент собирается в Docker и отдаётся API с того же origin. Redis обслуживает общие rate limits; PostgreSQL хранит все игровые данные и устойчивые очереди. Worker не является единственным способом завершить задачу: при запросе состояния и перед командой выполняется тот же `settle`, поэтому рестарт worker не теряет прогресс.

## Транзакция команды

Проверка сессии → Redis rate limit → `SELECT users FOR UPDATE` → проверка ключа и отпечатка → серверное начисление → проверка владения, ресурсов и требований → игровые изменения и ресурсный журнал → новая ревизия → сохранение ответа под ключом → COMMIT. Ошибка откатывает всю транзакцию. При обрыве ответа повторный запрос с тем же ключом не меняет состояние повторно.

Все писатели одного аккаунта, включая worker, используют ту же блокировку. Будущие взаимодействия двух игроков должны блокировать обе строки в стабильном порядке ID, а владение территорией/листингом — отдельной блокировкой объекта. Эта часть пока не реализована и не должна наследовать гарантии одиночной команды без тестов.

Серверная модель использует 16 таблиц. Не создаются заранее десятки пустых таблиц для нереализованных функций. Первая миграция — замороженная схема, а не импорт актуальных моделей. Последующие изменения только новыми Alembic revision.

## Время и экономика

Время — Unix seconds сервера. Производство целыми минутами: используется набор построек, готовых на начало каждой минуты. Неполная последняя минута не начисляется повторно. При недостатке энергии производственные здания останавливаются. НПЗ потребляет 2 нефти на 3 топлива; переполненный выходной склад останавливает цикл без расхода входа. Нет клиентских операций начисления.

Офлайн-период ограничен последними 24 часами; более раннее время отбрасывается. В этом срезе нет изменения уровня/эффективности зданий, событий или расхода энергии топливом. Перед их добавлением требуется журнал временных сегментов эффективности.

## Синхронизация

Сервер увеличивает ревизию при изменении состояния и хранит событие. WS принимает токен первым сообщением, а не в URL. После подключения отправляется полный разрешённый snapshot. Каждые 2 секунды проверяется новая ревизия; при её изменении отправляется snapshot, иначе heartbeat. Клиент игнорирует снимок со старой ревизией. Это простая snapshot-модель, не обещание уже реализованного delta streaming. Для масштаба потребуются outbox, Redis pub/sub, retention событий и контроль числа WS-сессий.

## Бой

Сервер проверяет номер раунда и принадлежность боя, сохраняет приказ и результаты. Случайный множитель выводится из SHA-256(seed, turn, actor), поэтому результат стабилен. Seed не раскрывается до конца боя. Урон сторон применяется одновременно. Первая PvE-операция персональная: она не изменяет глобальное владение. После победы новая попытка этой миссии запрещена. Награда и экземпляр предмета создаются в той же транзакции.

В срезе нет линии видимости, подавления, маршрутизации вокруг препятствий и расхода боеприпасов. Избыточное описание этих механик в UI исключено. Все показатели вымышленные, служат только игровому балансу.

## Дополнение 31: единая RPG-система

Существующая таблица `player_heroes` развивается в полноценную модель героя, без второй параллельной системы командиров. В срезе: шесть вариантов, один выбор, XP, один тактический слот и один тип лута. Эффекты: Raven +5% урона, Valkyrie +1 радиус начального обзора, Titan −5% получаемого урона, Phoenix +10 HP восстановления, Ghost +1 металл/мин карьера, Storm перемещение до двух гексов учебного боя. Эти тестовые эффекты не являются окончательным балансом специализаций.

`equipment_instances.id` — стабильный UUID, `owner_id` — единственный текущий владелец; `source_id` уникален. `item_ownership_history` хранит происхождение. Снятие/экипировка выполняются под блокировкой аккаунта; в активном бою смена запрещена. Боевой бонус ограничен 10% на уровне расчёта. Сейчас доступен только +3% от полевого модуля.

Далее: definition-таблицы, 8 слотов и их уникальные ограничения, коллекции с атомарным счётчиком тиража, affixes, 6 редкостей, 3 комплекта, история улучшений, loot rolls, уникальные artifact discoveries, server-side caps. Не публиковать UUID как доказательство блокчейн-NFT: это внутриигровые коллекционные записи.

IRON MARKET: отложен полностью. До его реализации требуется решение об операторской модели, возвратах и вознаграждении продавца. Никаких обещаний вывода Stars. Экипированный/выставленный/заблокированный предмет должен иметь взаимоисключающие состояния. Покупка должна блокировать листинг и предмет, фиксировать платёж по уникальному Telegram charge ID и атомарно менять владельца. Возврат требует отдельной политики при последующей перепродаже. Текущая таблица владения расширяется, а не дублируется в независимом инвентаре.

## Визуал

PixiJS WebGL, axial координаты, изометрическая проекция, сенсорная камера. Геометрия оригинальная, написана кодом; это технические ассеты. Отдельный художественный этап: портреты, full-body варианты, изображения экипировки, атласы зданий в 4 стадиях. Сейчас нет заявлений о реализованных texture atlases, streaming ассетов, полноценном LOD, frustum culling и 30/60 FPS. Глобальная карта ограничена одним видимым стартовым чанком; подгрузка по движению камеры — следующая задача.
